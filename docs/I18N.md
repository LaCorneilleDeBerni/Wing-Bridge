# Internationalisation (i18n)

> Wing Bridge is **bilingual French / English**, with a flag selector in the
> header. French remains the default language and the fallback.

This document describes **how it works**, the **conventions**, and the
**accepted limitations**. The translator's guide (which only touches the values)
is in `src/locales/README.md`.

---

## In brief

| Piece | File | Role |
|---|---|---|
| Client engine | `src/ui/i18n.js` | `t()`, `tHtml()`, `plural()`, `appliquerLangue()`, `LANG` |
| Server engine | `src/wing_i18n.py` | `L()`, `L_en()`, `plural()`, `rendre()`, `LANGUE` |
| FR catalogue | `src/locales/fr.json` | the reference — every key exists here |
| EN catalogue | `src/locales/en.json` | English translation, **up to date** (Phase 3 done) |
| Catalogue route | `wing_handler._get_locale` | serves `/locales/<lang>.json` (same `no-store` rule as `/ui/*.js`) |
| Language route | `wing_handler._post_lang` | `POST /api/lang {"lang":"fr"\|"en"}` → sets `wing_i18n.LANGUE` |
| Selector | header of `src/wing_ui.html` | `🇫🇷` / `🇬🇧` buttons → `appliquerLangue('fr' / 'en')` (which also calls `/api/lang`) |
| Guard | `smoke_test.py` → `test_i18n` | keys present on both sides, parity, no string-gluing — **client (a–f) AND server (g–i)** |

## The principle: plain French + `data-i18n`

The markup **keeps the French written out in full**, and **doubled** by a
`data-i18n` attribute:

```html
<h2 data-i18n="ui.bridge.journal.titre">Journal</h2>
```

- Language = French, catalogue loaded → `appliquerLangue('fr')` replaces
  “Journal” with `fr.json["ui.bridge.journal.titre"]` (same text).
- Language = English → replaces it with `en.json[...]`.
- **Catalogue not (yet) loaded, or route unreachable** → `appliquerLangue`
  doesn't touch the DOM: the markup's “Journal” stays displayed. No flicker of a
  raw key, and the app stays usable in French even if the catalogue is missing.

Strings **born in the JavaScript** (labels that follow the state, log messages,
tables built in JS) go through `t()`:

```js
bb.textContent = t("ui.bridge.bouton.arreter");           // "⏹ Arrêter le bridge"
rt.textContent = t("ui.bridge.recuperation.txt",          // interpolation
                   { nom: s.recovery.name, quand: quand });
```

### Attributes

| Translated HTML attribute | Marker |
|---|---|
| node text | `data-i18n="key"` |
| `innerHTML` (the value contains tags) | `data-i18n-html="key"` |
| `title` | `data-i18n-title="key"` |
| `placeholder` | `data-i18n-placeholder="key"` |
| `aria-label` | `data-i18n-aria-label="key"` |

## Loading the catalogue — and why a route

Two approaches were possible: `fetch()` of a static embedded file, or a
**dedicated server route**. Chosen: **dedicated route** `GET /locales/<lang>.json`
(`wing_handler._get_locale` → `wing_ui._lire_locale`, whitelist of language
names, `no-store` cache).

**Why**, verified in both modes:

- **Frozen app (PyInstaller)**: the files are under `sys._MEIPASS`, not at a
  path served as-is. A `fetch('/locales/fr.json')` to a file server doesn't
  exist here — *the engine* has to answer. The route reads via
  `_RES_DIR / "locales"`, exactly like `_lire_js` for `ui/*.js`.
- **Run from source**: `_RES_DIR = wing_ui.py's folder`, the route reads
  `src/locales/`. Identical.

A single code path for both, modelled on what already works for the JS.

`src/ui/i18n.js` loads **both** catalogues at startup (`chargerCatalogues()`),
exposes `window.I18N_PRET` (a `Promise`), and `init.js` — loaded last —
**waits for `I18N_PRET`** before the first render, so the dynamic labels come
out in the right language from the start.

## Resolving a key — `t(key, params)`

1. `CATALOGUE[LANG][key]` if it exists;
2. otherwise `CATALOGUE.fr[key]` (**French fallback** — every key is meant to be
   there);
3. otherwise the **key itself** (last resort; should never be displayed).

Then interpolation: each `{name}` in the string is replaced by `params.name`. A
gap with no value is left literally (`{name}` visible = a spottable bug).

`tHtml()` is the same engine: it exists separately so the intent “this value
contains tags and will go into innerHTML” is legible at the call site — and
verifiable by the smoke test.

> 🔒 **Since 25/09/2026 (security audit), `tHtml()` escapes its
> parameters.** The template comes from the catalogue (i.e. from us) and may
> carry tags; the parameters carry data — key name, keystroke, encoder
> attribute, often taken from an imported profile — and interpolating them raw
> into `innerHTML` let a profile run JavaScript. A parameter that is itself
> HTML already produced by `tHtml()` is wrapped in `brut(…)` (ui/core.js), and
> **only** that one. `esc()` now also escapes `'` and `"`. Check
> `test_xss_profil_importe`.

## Key naming convention

- **Flat** (no nested objects in the JSON), **hierarchical by dots**.
- **Namespace first**:

| Namespace | For | Resolved by |
|---|---|---|
| `ui.*` | the interface (markup + JS labels) | client `t()` |
| `journal.*` | server log lines | server `L()` (display) / `L_en()` (disk) |
| `err.*` | `raison`/`message` of JSON responses shown in the UI | server `L()` |
| `firmware.*` | steps of the firmware capture wizard | server `L()` |
| `diag.*` | diagnostic report | server `L_en()` **only** (always English) |
| `aide.*` | help text (“?” pop-ups + Help tab) | client `t()`/`tHtml()` |

- Then, **the location**: `ui.<tab>.<block>.<element>` —
  `ui.bridge.journal.titre`, `ui.param.dmx.titre`, `ui.entete.bouton.enregistrer`.
- A `_tip` suffix for the `title` associated with an element:
  `ui.entete.bouton.enregistrer` / `ui.entete.bouton.enregistrer_tip`.

## The golden rule: whole sentences with gaps, never string-gluing

**One displayed sentence = one key = one complete string**, with `{gaps}` where
the text varies.

```js
// ❌ NO: the code assembles pieces of a SENTENCE (prose literals)
"Fader " + i + " rattrapé"
t("mot.fader") + " " + i + " " + t("mot.rattrape")

// ✅ YES: one key, one sentence, gaps
t("journal.fader.rattrape", { n: i })
//  fr.json : "journal.fader.rattrape": "Fader {n} rattrapé"
//  en.json : "journal.fader.rattrape": "Fader {n} caught up"

// ✅ TOLERATED: gluing a t(...) to PURE MARKUP (assembling HTML is not
//            splitting a sentence)
"<td><b>" + t("ui.x.libelle") + "</b></td>"

// ✅ TOLERATED: gluing two ALREADY-translated blocks, or a function call
t("ui.sante.osc.muet", { port: p }) + oscPourquoi(s)   // 2nd = a function, not a literal
```

**Why**: word order, agreement, the position of the number change from one
language to another. “Fader {n} rattrapé” and “Fader {n} caught up” don't have
the same structure; in German the participle goes to the end. A patchwork of
fragments freezes French grammar into every language — and produces
translations the translator cannot fix, because they never see the whole
sentence.

The smoke test (`test_i18n`, sub-check (e)) refuses the build if it sees a
`t(...)` / `plural(...)` **glued with `+` to a prose string literal**. Pure
markup (`"<b>"`, `"</td>"`), variables and adjacent function calls do pass: the
fault we hunt for is the hard-coded sentence fragment, not every concatenation.

## Plural — `plural(key, n, params)`

Same principle as `t()`, but the **form** is chosen according to `n`. The key is
a **prefix**; the forms are sub-keys of the catalogue:

```json
"ui.x.frappes.one":   "{n} frappe déjà prise",
"ui.x.frappes.other": "{n} frappes déjà prises"
```

```js
plural("ui.x.frappes", n, { items: liste })   // → form + interpolation ({n} included)
```

`REGLES_PLURIEL` in `i18n.js` carries an `n → category` function per language:

- `fr`: `n ≤ 1 → "one"`, otherwise `"other"` (French puts “0” in the singular);
- `en`: `n === 1 → "one"`, otherwise `"other"`.

`fr.json` and `en.json` therefore only have `.one` / `.other`. Languages with
**multiple plurals** (Polish, Russian, Czech, Arabic…) add `.few`, `.many`…
(CLDR categories `zero`/`one`/`two`/`few`/`many`/`other`) and the corresponding
rule in `REGLES_PLURIEL`. An explicit table rather than `Intl.PluralRules`:
“download and run”, identical behaviour whatever the version of the JS engine.

`test_i18n` (b) checks that every `plural("X", …)` has `X.one` **and** `X.other`
on both sides.

## Adding a sentence (developer)

| Case | What to do |
|---|---|
| Text in `wing_ui.html` | add `data-i18n="ui.…"` (or `data-i18n-title`…), keep the plain French in the tag, add the key to **both** JSON files |
| String in `ui/*.js` | replace the literal with `t("ui.…")` or `t("ui.…", { n: x })`, add the key to **both** JSON files |
| Injected HTML (`innerHTML`) | `tHtml("ui.…")` — the value may contain tags |

The smoke test's `test_i18n` check verifies, on every build:

**Client side:**

- (a) every `data-i18n*` key in the HTML exists in `fr.json` **and** `en.json`;
- (b) every `t()` / `tHtml()` / `plural()` key **already written** in the JS
  points to a key that exists on both sides;
- (c) `fr.json` and `en.json` have **exactly** the same set of keys;
- (d) **no** leaf element in the HTML (`h1..h4`, `button`, `label`, `summary`,
  `option`) with > 2 words of visible text without a `data-i18n` — blocking;
- (e) no `t(...)` glued with a `+` (no sentence assembly);
- (f) for every `data-i18n*` key, the **plain French text of the markup** is
  identical (up to whitespace) to `fr.json[key]`. `fr.json` is the reference;
  the markup is just a snapshot kept in sync.

**Server side** (see “Server side” below):

- (g) every `journal.` / `err.` / `firmware.` / `diag.` key **cited in a
  `wing_*.py`** exists in `fr.json` **and** `en.json` (plurals: `.one` **and**
  `.other`);
- (h) server anti-gluing heuristic: no `L("…") + "prose"` /
  `plural(…) + "prose"` (pure markup and adjacent variables/functions pass, as
  in (e));
- (i) `wing_diagnostic.py` calls **only** `L_en()` / `_LE()`, never a bare
  `L(` — the diagnostic report must stay English whatever the language.

**Non-blocking note**: `test_i18n` also counts, on every build, the keys where
`en.json[key] == fr.json[key]` (excluding `diag.*`) and lists them if the list
is non-empty — not a failure (some equalities are legitimate: `Bridge`, `Type`,
`ID`, an MA3 name…), but a signal to re-read so an accidentally untranslated key
doesn't slip through silently on a future addition.

## Adding a language (contributor)

Step-by-step guide: `src/locales/README.md`. **All the touch points**, not to be
forgotten (the smoke test catches most, but not the flag):

| # | File | What to do there |
|---|---|---|
| 1 | `src/locales/xx.json` | **create** — a copy of `en.json`, values translated (never the keys). `aide.*` (“?” pop-ups + Help tab) is in this same file, like every other namespace — no separate file. |
| 2 | `src/ui/i18n.js` → `LANGUES_SUPPORTEES` | add `"xx"` — this is what triggers the `fetch` of the catalogue at startup |
| 3 | `src/ui/i18n.js` → `REGLES_PLURIEL` | add the `xx` rule **if the language has more than two forms** (otherwise the `fr` fallback is enough) |
| 4 | `src/wing_i18n.py` → `_REGLES_PLURIEL` | add the `xx` rule (**mirror** of point 3 — serves as a whitelist for `poser_langue()` **and** as the server plural rule) |
| 5 | `src/wing_ui.py` → `LOCALES` | add `"xx"` — the **whitelist** of the `/locales/xx.json` route; without it the route returns 404 |
| 6 | `src/wing_handler.py` → `_post_lang` | nothing to do: validation already goes through `wing_i18n.poser_langue` (point 4) |
| 7 | `src/wing_ui.html` → header | add a `<button id="langXx" onclick="appliquerLangue('xx')">🇽🇽</button>` in `.langsel`, and handle `langXx` in `appliquerLangue` (highlighting the active one) |
| 8 | PR | propose the change |

⚠️ The `diag.*` namespace of `en.json` is **already in English** (not a copy of
the French): a new language translates it like the rest, but the diagnostic
report itself stays **always English** (`L_en`), whatever the chosen language.

**Text length — the interface must tolerate ± 35 %.** German expands (often +30
to +35 % vs French), English shortens (often −15 to −25 %). A button label, a
fader label, a card title must stay legible both ways: no fixed width that
truncates, no layout that breaks if a string doubles in length. To be checked by
eye on each tab after adding a language.

**The tab bar (`<nav>`) and the top bar (`<header>`) are pinned.** Both are
flexboxes where each button sized itself to its text, so they visibly shifted on
FR → EN (shorter English labels). Each button now carries a per-button
`min-width` set to `max(FR width, EN width)` measured in the browser (WebKit) —
so the bar keeps the same width in both languages and no label is clipped:

- `<nav>`: `nav button:nth-child(n)`, plus `overflow-x: auto` so a very narrow
  window scrolls instead of breaking. `nth-child` rather than `[data-tab="…"]`
  because the smoke test `test_onglets` scans the file for `data-tab="…"` and
  would miscount a CSS selector as an extra tab.
- `<header>`: `.topbar > header > button:nth-of-type(n)` — the child combinator
  skips the language-selector buttons (inside `.langsel`), and the `.topbar`
  prefix skips the modal `<header>`s (their `Fermer` / `Close` button). The
  `.pill` (`Profil :` / `Profile:`) is left alone: the two labels differ by
  < 4 px, it sits in the flexible space next to the auto-margin of `h1` so it
  does not push the buttons, and it already resizes with the profile name.

**When you add a language**, re-measure these labels: if one is wider than its
slot, bump that `min-width` (the values are commented one by one in the
`<style>`).

## Server side

The `src/wing_i18n.py` engine is the **Python mirror** of `ui/i18n.js`: same
catalogue files (`locales/fr.json` + `locales/en.json`, read via
`wing_ui._lire_locale` — same cache, same whitelist), same `{name}`
interpolation, same plural table.

### The five surfaces and their language

| Surface | Language | How |
|---|---|---|
| Log **displayed** in the interface (Bridge tab) | current language | `wing_reglages.journal_affiche()` → `/api/status` `log` field |
| `wing_server.log` file **on disk** | **always English** | `wing_reglages._log_to_file()` → `L_en` |
| `raison` / `message` of JSON responses **shown in the UI** | current language | `_L(...)` (`err.*`) at the call site |
| Firmware wizard steps (`_phase` / `_etape`) | current language | `wing_i18n.L(...)` (`firmware.*`) — Windows wizard |
| Diagnostic report (`build_diagnostic`) | **always English** | `wing_diagnostic._LE(...)` = `L_en` (`diag.*`), guaranteed by (i) |

### `L` vs `L_en`

- `L(key, **params)` → resolves in `wing_i18n.LANGUE` (fallback `fr`, then raw
  key). For everything that follows the app's language.
- `L_en(key, **params)` → forces English (fallback `fr`). For the **disk** and
  the **diagnostic** — those two go to a maintainer, never in the user's
  language.
- `plural(key, n, **params)` → mirror of the client `plural()`.
- `LANGUE`: module variable, default `"fr"`, set **only** by
  `wing_i18n.poser_langue()`, called by `POST /api/lang`. The client
  (`appliquerLangue()` in `i18n.js`) does this POST best-effort in addition to
  its DOM translation.

### The log in keys

`wing_reglages.LOG` (the in-memory deque) no longer stores formed strings but
**structured entries** `{hc, hl, cle, params, n, brut}`:

- `cle` set → **translatable** line, re-resolved on EVERY read: in `LANGUE` for
  `/api/status`, as `L_en` for disk. A language change therefore re-translates
  the whole in-memory history on the next poll; lines already written to disk
  don't move (normal — the file is English).
- `brut` set → **pass-through**: text already formed that doesn't need
  translating (hex dumps, stack traces, MA3 command echoes in console mode,
  `ENC1 Pan +12`, `FADER F1 → …`). Copied verbatim on both sides.

`log(cle_ou_texte, **params)` chooses: a first argument starting with a known
namespace (`journal.` `err.` `firmware.` `diag.`) → a keyed entry; otherwise →
raw. `log_plural(cle, n, **params)` for lines whose form depends on a count.
`_msg` (`wing_init`), `_suivi_dit` (`wing_faders`), `_etape` / `_phase`
(`wing_firmware_capture`), `_log` (`wing_firmware_capture`) all forward
`**params`.

### What deliberately stays in French (judged case by case)

- **Console mode** (`wing_boutons`): the MA3 command echoes (`CONSOLE : …`,
  `EXEC : …`, `BUFFER : …`, `→ "…"`) — an expert diagnostic stream, mostly MA3
  syntax, a one-word tag.
- The **capture wizard** (`wing_firmware_capture`, Windows/exploratory): the
  concatenated residual warnings (`residu` / `residu_reprise` / `note_finale`),
  the raw status of the elevated PowerShell script (`_etape(et)`).
- A few `raison` values **never displayed**: HTTP protocol errors
  (`{"error": "not found"}`), defensive guards only a tampered client can
  trigger (`langue inconnue`, `mode inconnu`), state fields initialised to `""`.
  Full list in the `err.*` commit messages.

## Known, accepted limitations

- **EN translation**: `en.json` is translated (Phase 3 done) — MA3 vocabulary
  kept as-is, literal MA3 keywords not translated. A non-blocking `test_i18n`
  check counts the keys still identical to `fr.json` (excluding `diag.*`, whose
  few neutral labels — `Date`, `macOS`, `OSC`… — are legitimately the same
  words in both languages): to watch on every key addition, so an untranslated
  one isn't left in silence.
- **Complex plurals**: only the `fr`/`en` rules are written. The others are
  added in `REGLES_PLURIEL` (see above).
- **Right-to-left languages** (Arabic, Hebrew): **not handled**. `dir="rtl"`
  will need to be set on `<html>` in `appliquerLangue` and the CSS checked the
  day such a language is added.
- **Numbers, dates, units**: no localised formatting for now
  (`Intl.NumberFormat` / `DateTimeFormat` to be wired in if the need appears).

## If we outgrow this solution one day

The chosen form — **flat keys + whole sentences with `{name}` gaps** — is not a
dead end:

- **Weblate** imports the flat JSON as-is (community translation platform,
  self-hostable).
- A conversion to **gettext (`.po`)** or **ICU MessageFormat** is scriptable:
  key → `msgid`, value → `msgstr`, `{name}` → `%{name}` or `{name}`. Nothing to
  re-enter.

The exit cost is a script, not a rewrite — that is the reason for the choice.
